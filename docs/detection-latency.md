# 앱 감지가 느렸던 이유

AppMixer를 쓰다 보니 소리 나는 앱을 켜도 목록에 늦게 뜨는 문제가 있었습니다. 측정해 보니 원인은 두 가지였습니다. 지켜보던 속성의 변경 이벤트가 오지 않았고, 오디오 장치 시작이 메인 스레드를 막고 있었습니다. 이 글은 원인을 찾은 과정과 수정 내용을 정리한 기록입니다.

- 환경: MacBook Air M1, macOS 27.0.1, 블루투스 출력 장치
- 측정용 소리: `afplay`로 재생한 들리지 않을 만큼 작은 소리와 무음 파일

## 처음 구조

코드는 이벤트 방식이었습니다. 시스템의 프로세스 목록과 각 프로세스의 `kAudioProcessPropertyIsRunningOutput`을 구독하고, 이벤트가 오면 목록을 다시 읽습니다. 구조만 보면 지연이 거의 없어야 합니다. 그래서 추측으로 고치지 않고, 재생 시작부터 각 단계까지 걸린 시간을 먼저 쟀습니다.

## 원인 1: 오지 않는 변경 이벤트

재생을 시작하고 감지까지 걸린 시간을 2회 쟀더니 결과가 이랬습니다.

| 시도 | 결과 |
|---|---|
| 1 | 12.8초. 출력 이벤트가 아니라 프로세스 목록 이벤트가 왔을 때 감지 |
| 2 | 20초 안에 감지하지 못함 |

값 자체가 늦게 바뀌는지, 알림만 오지 않는지 구분하려고 20ms 간격 폴링과 이벤트를 나란히 비교했습니다.

| 재생 파일 | 값이 1로 바뀐 시점 (폴링) | 변경 이벤트 |
|---|---|---|
| 작은 소리 | 225ms | 11초 동안 안 옴 |
| 무음 | 145ms | 11초 동안 안 옴 |
| 작은 소리 | 222ms | 11초 동안 안 옴 |

값은 0.2초 안에 바뀌는데 이벤트만 오지 않았습니다. 앱은 다른 프로세스가 켜지거나 꺼져서 목록이 우연히 갱신될 때까지 새 앱을 알 수 없었던 것입니다.

그럼 어떤 이벤트가 오는지 보려고 프로세스 객체에 와일드카드 리스너를 달았습니다.

```
203ms process: pir?    kAudioProcessPropertyIsRunning
205ms process: pdv#    kAudioProcessPropertyDevices
```

5초 동안 `piro`(`IsRunningOutput`)는 한 번도 오지 않았고, `pir?`(`IsRunning`)는 왔습니다. 소리가 멈출 때도 이벤트가 오는지는 테스트 프로세스 자신의 출력을 시작하고 멈춰서 확인했습니다.

```
  42ms IsRunning 이벤트, 이때 IsRunningOutput=1
2144ms IsRunning 이벤트, 이때 IsRunningOutput=0   (정지 호출 4ms 뒤)
```

시작과 정지 모두 이벤트가 오고, 그 시점에 `IsRunningOutput` 값도 이미 맞았습니다. 그래서 구독 대상만 `IsRunning`으로 바꾸고, 값을 읽는 코드는 그대로 뒀습니다.

## 원인 2: 메인 스레드를 막는 장치 시작

첫 번째 수정 뒤 실제 앱에서 재 보니, 앱을 켠 직후의 첫 재생만 약 4초 늦었습니다. 로그에서 탭 준비 후 완료까지 메인 스레드가 6.3초 동안 멈춘 구간이 보였습니다.

볼륨을 저장해 둔 앱은 Process Tap을 시작합니다. 이 작업이 메인 스레드에서 끝날 때까지 UI와 이벤트 처리가 모두 멈춥니다. 장치가 이미 동작 중일 때 별도 스크립트로 잰 탭 생성 전체 시간은 30~60ms였습니다. 그래서 출력 장치가 준비되기를 기다리는 시간으로 보지만, 이 부분은 직접 분리해서 확인하지는 않았습니다.

`AudioDeviceStart`만 옮겼을 때는 멈춤이 2.1초 남았습니다. 그래서 `AudioDeviceCreateIOProcIDWithBlock`까지 전용 직렬 큐로 옮겼습니다. 정지와 해제도 같은 큐에서 처리합니다.

- **직렬 큐를 쓴 이유:** 이전 탭의 정지가 새 탭의 시작보다 먼저 끝나야 합니다.
- **메모리 해제 순서:** IO 콜백이 읽는 볼륨 값 메모리는 장치를 멈춘 뒤에 해제합니다.
- **시작 실패 처리:** 앱이 음소거된 채 남지 않도록 메인 스레드로 알려서 탭을 정리합니다.

## 결과

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 재생 시작 → 목록 표시 | 12.8초, 또는 20초 넘게 감지 못 함 | 0.17~0.22초 (3회) |
| 탭 시작 중 메인 스레드 멈춤 | 6.3초 | 로그 기준 0ms |

수정 전 감지 시간은 앱과 같은 방식으로 구독한 측정 스크립트에서, 수정 후 값은 실제 앱에 임시 로그를 넣어 쟀습니다. 측정 횟수가 적고 한 대의 Mac, 한 가지 출력 장치에서 잰 값이므로 대략적인 수치로 봐 주세요.

## 남은 한계

- **IO가 이미 돌고 있는 앱:** `IsRunning`은 출력만이 아니라 프로세스 전체의 오디오 IO 상태입니다. 그래서 마이크와 스피커를 함께 쓰는 앱이 출력만 시작하거나 멈추면 값이 그대로라 이벤트가 오지 않을 수 있고, 이 경우 다음 갱신 때 목록에 반영됩니다. 헤더 설명을 보고 판단한 것이고 직접 재현하지는 않았습니다.
- **다른 환경:** `IsRunningOutput` 이벤트가 오지 않는 현상이 다른 macOS 버전에서도 같은지는 확인하지 못했습니다.
- **오디오 시작 지연:** 목록에는 바로 떠도, 출력 장치가 준비되는 동안 소리는 늦게 나올 수 있습니다.

## 정리

- 구조가 이벤트 방식이어도 이벤트가 실제로 오는지는 재 봐야 알 수 있습니다.
- 폴링과 이벤트를 나란히 놓으면 값이 늦는지 알림이 늦는지 바로 구분됩니다.
- 와일드카드 리스너를 달면 시스템이 실제로 보내는 이벤트를 볼 수 있습니다.
